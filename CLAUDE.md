# Aidyn Chronicles Enhanced

A PC reimplementation of Aidyn Chronicles: The First Mage (N64), forked from HBHT (ADR 0030). It runs on content imported from a user-supplied ROM and has a plugin-based mod system. M1, M2, M3 (Fight) and M4 (the prologue, played side by side with the emulator) are playable, and 2.10's events and triggers carry the cinematics. Next is Phase 4, content parity. The roadmap's [Where things stand](docs/roadmap.md#where-things-stand) has the rest.

## Glossary

Use these words in code and docs. Where the original's name clashes with ours, use ours and cite the original's in a `<c>` tag (ADR 0009). The original's names are the ones the ROM gives (the debug build's strings) or the symbol map's; no third-party decompilation's names are cited (ADR 0030).

| Term | Means | Don't confuse with |
| --- | --- | --- |
| **Trek** | Free exploration, the original's out-of-combat mode (`gametrek.cpp`). | The systems trek shares with combat, which aren't trek's (ADR 0009). |
| **Combat** | Turn-based fighting (`gameCombat.cpp`). The player-facing docs call it battle mode. Arenas are the Battle arenas map set. | |
| **Tick** | 1/60 s, the core's unit of time. The core steps one tick at a time (ADR 0017). | A **frame**: one rendered frame of the original, covering `delta` ticks (1–6). **Cadence** is how the port matches per-frame behaviour: a 30 fps frame, 2 ticks. |
| **Borg** | An asset in the ROM's archive, by type (Borg1 texture … Borg13 script) and archive index. | |
| **Scene** | A Borg5: a tree of transforms with models, a camera and lights. Record `aidyn:scene/0x…`. | A Godot scene (`.tscn`). Say "Godot scene" for those. |
| **Actor** | A Borg7: a scene with a state machine of animations. Record `aidyn:actor/0x…`. | The original's `Actor::` functions, which move a **body** through the world: the player, an NPC or a combatant. That code is in `Movement` and `Physics`. |
| **Request** | The animation number the game asks an actor for (0 idle, 2 walk, 3 run, …). | An actor's states. |
| **Entity** | An EntityDB record: a kind of character or creature, with its stats. Record `aidyn:entity/0x…`. | An ECS entity. |
| **Map set** | One of the 17 grids of chunks: the Overworld, the Gwernia interiors, the Battle arenas and so on. Record `aidyn:mapset/<n>`. | |
| **Chunk** | One cell of a map set, named by row letter and column (I08, M07): a Borg9 and up to two scenes. The 3×3 around the player are loaded (the original's `ZoneEngine`; ours is the chunk streamer, which our `ZoneEngine` holds). | |
| **Map** | Record `aidyn:map/0x…`: one Borg9, a chunk's collision and map objects. | The world map in the pause menu, and the minimap. |
| **Map object** | An object a Borg9 places: a scene, container, teleporter, trigger, monster party and so on. Record `aidyn:voxel/0x…/<n>`, after the original's own name, a voxel object. | A **voxel** alone: the original also uses the word for a chunk's collision (`CollideCollisionSphereWithVoxelPolys`). Say map object in code and docs, and voxel only in record IDs. |
| **World** | The worldspace: the loaded map set. `CollisionWorld` is its loaded collision. | The original's `World`, which is the calendar, time of day, weather and terrain. |
| **Flag** | One of the 5,627 event flags in `GameStateFunnel`. A flag is **plain** (set by scripts, map objects or code) or **derived** (computed from others). Record `aidyn:flag/<n>`. | "Game state" and "event flag" mean the same thing. |
| **Script** | A Borg13: a conversation, cut-scene, backdrop or sign. | A **Lua script**, ADR 0008's layer 4. Always say "Lua" for those. |
| **Cut-scene** | A script that moves the camera and actors in the game world. | A **cinematic**: one of the four pre-animated scenes (`CinematicStruct`). |
| **Base plugin** | `aidyn.base`, the plugin the importer writes from the ROM. The runtime and the editor read only plugins (ADR 0001). | |
| **Checkpoint** | A save state the user captured by playing (see the reference rig). | |

## Code

A .NET 10 solution (`AidynEnhanced.slnx`, SDK pinned in `global.json`), laid out per ADR 0002, named `AidynEnhanced.*` (ADR 0033: Aidyn Chronicles Enhanced is the name players see, Aidyn Enhanced the code's, and ACE the branding's in `assets/branding`; `aidyn` stays only for the game's names and the imported data, such as the `aidyn:` record IDs and `aidyn.base`). Each system's doc names the classes that port it.

- `src/AidynEnhanced.Rom`: everything that reads the ROM (ADR 0001). Identification and per-version offsets (`RomImage`, `RomVersions`), the decompressors (`Compression/`), the Borg archive (`Borg/`), the DB block's records (`Db/`), the text cipher and string tables (`Text/`), the graphics Borgs from textures to actors and particles, with a glTF writer (`Graphics/`), Borg13 scripts (`Dialogue/`), Borg11 samples and Borg12 sequences (`Audio/`), map sets and Borg9 (`Maps/`), the flags engine code names and the tables it keeps them in (`Quests/`), the content tables in the code segment (`Engine/`), the importer (`Import/`), and a reader for the checkpoints' RAM, which needs no ROM and turns one into a save, with the original's saves and the Controller Pak they're kept in (`Rig/`).
- `src/AidynEnhanced.Plugins`: the plugin format (ADRs 0004, 0005): record IDs, loading with field-level merges and the conflict report, the typed records (`Records/`), the catalog the editor browses (`PluginCatalog`, with `MapPlacements` for where a map sits and `MapObjectKinds` for what its objects are called), the quest atlas's index over the records (`QuestIndex`), the readers of the importer's glTFs (`Assets/`, all through `GlbReader`, with `SceneNames` and `ExtrasKeys` the names and keys the importer writes and the readers look for) and the save format (`Saves/`). The importer writes the base plugin with these types, and the runtime and editor read it.
- `src/AidynEnhanced.Core`: the headless rules core (ADR 0003), by subsystem, not game mode (ADR 0009): `Physics`, `Movement` (bodies, the player's among them, setting them down, pushing and shadows), `Cameras`, `Calendar` (the clock and the weather), `Actors` (Borg7 state machines, timed and moving bodies by their scenes' animations, `ActorMotion`), `Scenes` (billboards, scrolling textures, draw distance), `Flags`, `Scripts` (the Borg13 VM and cut-scenes), `Rng`, `Characters`, `Items`, `Combat` (a battle, `Battle`, from its setup to its rewards, with the AI and the battle screen's state), `Magic` (casting, and where spells' and potions' effects land, ADR 0021), `MapObjects`, `Chunks` (which chunks are loaded, with their collision and map objects, and the zone engine, `ZoneEngine`, the world trek and a cut-scene's stage play in: the chunks with their sounds and lights, the music, the weather's step and rain), `Ui` (text layout and the menus' state, which the Godot views draw), `Trek` (trek's loop, `TrekLoop`, over a zone engine, and what's trek's alone: wanderers and conversations), `Sky`, `Lights` (light map objects and dynamic lights on bodies and actors), `Particles` (the particle pool, which actors' emitters and code's start in), `Cinematics` (the four pre-animated scenes, `CinematicPlayer`), `Events` (the named events and the plugins' triggers on them, `Triggers`) and `Audio` (the original's sequencer and mixer, `AudioEngine`, which renders the PCM the runtime plays). It's stepped per 60 Hz tick with per-frame behaviour matched to 30 fps (`Cadence`); turning across the ground (`Facing`) is shared at the root too. `GameState` at its root is the whole game, which a save snapshots and scripts run against, and `GameSession` beside it plays one, by what each tick is handed of the settings (`SessionSettings`, ADR 0023): it steps the mode that runs (trek, a cut-scene, or what holds them: the menu, a backdrop, the credits, a cinematic, the title screen over a new game, `TitleScreen`) and turns every ending into a `Transition` for the runtime to show, a battle's among them as a `BattleSetup` (`Combat`).
- `src/AidynEnhanced.Cli`: the `aidyn-enhanced` tool, `dotnet run --project src/AidynEnhanced.Cli -- <command>`. `import <rom>` writes `aidyn.base` to the data folder's `plugins` (`AIDYN_ENHANCED_DATA`, else `%LOCALAPPDATA%\AidynEnhanced`). `borg summary|dump`, `db dump`, `textures`, `scenes`, `dialogue`, `audio` and `strings`, each given the ROM, dump it for research into the gitignored `out/`. `flag <n>` and `conflicts` read the installed plugins, not the ROM: what sets, clears and reads a flag, and which fields more than one plugin patches. `schema <dir>` writes a JSON Schema per record type, for records and for patches, which editors validate mods by. `save new|from <checkpoint>|show <save>` makes and checks saves, in the data folder's `saves`, and `save pak|to-pak|from-pak <rom>` reads and writes the original's in the Controller Pak beside the ROM.
- `src/AidynEnhanced.Views`: what the runtime and the editor both draw with, a Godot class library (ADR 0022), in namespace `AidynEnhanced.Views` (not `AidynEnhanced.Godot`, which would hide Godot's own `Godot.Node` from every `AidynEnhanced.*` namespace): the N64 material (`N64Material`), the glTF loaders (`GlbFile`, `GlbScene`, `Models`), actors (`ActorAnimator`), the chunk scenery with its billboards, scrolling textures and mirrored meshes (`ChunkScenery`), particles (`ParticlesView`), the UI screen and its painter (`UiScreen`, `UiPainter`, `UiImages`), the conversation box and the Party tab (`ConversationBoxView`, `PartyTabView`), and the command line's parser and screenshot (`CommandLine`). It references `AidynEnhanced.Core` and `AidynEnhanced.Plugins`, and uses nothing of either Godot project. What a scene attaches by path (`Game.cs`, `Editor.cs`) stays in its project; the library's nodes are made by code.
- `src/AidynEnhanced.Game`: the Godot runtime (roadmap Phase 3, [runtime](docs/systems/runtime.md)). It loads plugins only, never the ROM, and draws what the core steps and carries out what it asks, keeping its loops thin (ADR 0012): trek's chunks, bodies, the sky, the HUD and the menus, over the views it shares with the editor (`AidynEnhanced.Views`). Run it with `tools/godot.ps1 --path src/AidynEnhanced.Game` after `aidyn-enhanced import`.
- `src/AidynEnhanced.Editor`: the editor (roadmap 0.6, [editor](docs/systems/editor.md)), which grows into the mod editor. It reads only the installed plugins, as OpenMW-CS does, and draws them with the runtime's code (ADR 0010). It holds the importer, and becomes the game's first run (ADR 0012). Code flows one way, from the core to the views to the runtime to the editor (ADR 0022): what both draw with is in `AidynEnhanced.Views`, and the runtime uses nothing of the editor's. Something built in the editor first, where it's easier to drive and screenshot, moves into the runtime once the runtime uses it, or into the views if the editor keeps it too. It holds a `GameState` of its own, a new game's, a checkpoint's or a save's, which scripts and pages play against and which it can save for the runtime. Run it with `tools/godot.ps1 --path src/AidynEnhanced.Editor`.
- `tests/AidynEnhanced.Core.Tests`, `tests/AidynEnhanced.Plugins.Tests` and `tests/AidynEnhanced.Rom.Tests`: `dotnet test` from the repo root. Real-data tests find ROMs in `roms/` (or `AIDYN_ENHANCED_ROMS`) by hash and skip when they're missing. `tests/AidynEnhanced.TestSupport` is what the three share: `TempPlugins` (a GUID-named temp folder of hand-written plugins), the small collision worlds in `Worlds`, and the record-ID shorthands (`Ids.Flag`, `Entity`, `Script`), which each test project imports globally. Rom.Tests' `TestRoms` also holds the checkpoint helpers, and `Na10Import` is the one NA 1.0 import its tests share.

## Questions over data

Many questions here are counts and cross-checks over thousands of records: how many containers have each reach, which talkers' cut-scenes name a point their chunk lacks, what every checkpoint holds at an address. Answer them with a script that does the looping and prints only the answer, rather than reading JSON or dumps into the context. One run replaces dozens of tool calls, and the script is the evidence behind the number that goes in a doc.

- **Over the plugins, in C#,** with the project's own types: a .NET 10 file-based app in the scratchpad, run with `dotnet run query.cs`. It takes about four seconds, and loading the base plugin about two.

  ```csharp
  #:project C:/path/to/aidyn-enhanced/src/AidynEnhanced.Plugins/AidynEnhanced.Plugins.csproj
  #:property PublishAot=false
  using AidynEnhanced.Plugins;
  using AidynEnhanced.Plugins.Records;

  var set = PluginSet.LoadInstalled(DataPaths.Plugins);
  var containers = set.All<MapRecord>("map").SelectMany(m => m.Objects).OfType<ContainerObject>();
  foreach (var g in containers.GroupBy(c => c.Reach).OrderBy(g => g.Key))
      Console.WriteLine($"reach {g.Key}: {g.Count()}");
  ```

  `#:project` needs the absolute path from the scratchpad. Without `PublishAot=false`, System.Text.Json refuses to load the records. Reference `AidynEnhanced.Core` as well to run the rules over the data (`GameState`, `ScriptRunner`, `MapObjectUse`), or `AidynEnhanced.Rom` for the ROM itself and the checkpoints (`AresCheckpoint`).
- **Over the original's code or the checkpoints,** loop `tools/n64dis.py` or `tools/bst.py` in one shell command, over the functions of a jump table or the eight states, or read the code index (`out/ghidra/<rom>.index.json`) and the pseudocode (`out/ghidra/<rom>.c`) in a script. `tools/ghidra.ps1 import` makes them.
- **A finding that should keep holding** becomes a real-data test instead.
- **Subagents** can work the same way: say so in the prompt when their question is about the data.

## Ground rules

- Never commit ROMs or anything derived from them. `roms/` is gitignored.
- **The project reads no third-party decompilation of the game** ([ADR 0015](docs/adr/0015-the-port-no-longer-reads-the-decomp.md), [ADR 0030](docs/adr/0030-the-project-is-aidyn-renewed.md)). Don't clone, fetch or search one, and tell subagents the same; none of their names are cited in the docs or code. [AidynEditor](https://github.com/TiberGuy/AidynEditor) (MIT) lives in the gitignored `ref/AidynEditor`; if it's missing, clone it there. [Aidyn ReChronicled](https://github.com/spitzdano/AidynReChronicled) lives beside the repo in `../AidynReChronicled`, cloned without its submodules; read it as [ADR 0032](docs/adr/0032-rechronicled-is-read-for-its-findings.md) says: never its `decomp/` or its symbol files, and what it says of the original is confirmed in the machine code.
- Settle what the original does from 1.0's machine code and the checkpoints, and cite the addresses in the doc. The [reference rig](docs/reference-rig.md#finding-the-originals-code) says how to find a system's code. The debug build's strings give the original's own names for its source files and some functions. Name the rest ourselves, and add each name settled to the symbol map (`tools/symbols/`) by [its rules](docs/reference-rig.md#the-symbol-map-roadmap-08): the original's own name from a string, else the port's, else one we coin. No name from a third-party decompilation goes in it.
- Where the port fixes one of the original's bugs, the user chose it, and the system's doc says so.
- The user reaches story checkpoints by playing the game. Don't drive gameplay in the emulator. Ask for in-game actions instead.
- Commit as you go, without asking: commit each finished slice of work once its tests pass, along with its doc and status updates.
- **Keep the main context for judgement and building.** Reading machine code fills a context fast, and Sonnet 5.5 subagents settle such questions well from the code. So send research into what the original does to a Sonnet subagent, batching what a slice needs into one run, and read the code yourself only for the lines you're porting. Point them at the docs, the symbol map and the rig's way of finding code, and have them return the names they settle for the map. Sonnet subagents also do well with well-scoped work: readers and importers over known layouts, indexes over plugin records, and real-data tests, which they check against the data before asserting. Give them the contract and the facts. Then review what comes back: spot-check a constant or two in the disassembly, and write findings into the system's doc straight away. They don't build the Godot projects, so build those yourself. Take an Opus subagent when Sonnet can't settle something, or two answers disagree.
